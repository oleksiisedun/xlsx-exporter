# xlsx-exporter

Google Apps Script library that exports a Google Sheets spreadsheet to a real `.xlsx` file, automatically flattening formulas that won't survive the trip to Excel (custom Apps Script functions, `IMPORTRANGE`, `GOOGLEFINANCE`, `QUERY`, dynamic/spill functions, and any formula referencing a sheet excluded from the export) to their last computed static value, while leaving Excel-compatible formulas live. See `README.md` for usage, deployment, and an architecture diagram.

## Project-specific conventions

- Plain `.js` Apps Script files — every function has a JSDoc comment with typed `@param`/`@returns`, per the global JS conventions.
- Apps Script concatenates every `.js` file in the project into one global scope (no import system). The file split (`Main.js`, `FormulaClassifier.js`, `FormulaParser.js`, `SpreadsheetDuplicator.js`, `CalculationWaiter.js`, `XlsxFetch.js`, `DriveUtils.js`, `Test.js`) is purely organizational.

## Architecture summary

`Main.js` is the public entry point (`exportSpreadsheetToXlsxBlob`, `exportSpreadsheetToXlsxFile`). It first waits (`CalculationWaiter.js`) for any source cell that would be flattened to finish calculating, then duplicates the source spreadsheet in Drive (`SpreadsheetDuplicator.js`), deletes excluded sheets from the copy, then flattens unsafe cells in the copy by reading formulas/values from the **untouched source** and writing static values into the **duplicate** — never the reverse, and the source is never mutated. Each cell's safe/unsafe classification (`FormulaClassifier.js`) relies on regex-based extraction of function names and sheet references from the formula text (`FormulaParser.js`); `FormulaClassifier.js` also exposes `getFlattenColumnIndices`, the single source of truth for "which cells in a row get frozen into the export," shared by both the flatten step and the calculation wait. Once flattening is done, `XlsxFetch.js` fetches the real `.xlsx` bytes via Google's native `/export?format=xlsx` endpoint, and the temporary Drive copy is deleted with retry in a `finally` block. `DriveUtils.js` also sweeps orphaned temp copies from previous runs (see design decisions below) and saves the resulting Blob to a Drive folder.

## Key non-obvious design decisions (read before changing flatten logic)

- **Any cell with no formula of its own is also rewritten from the source**, not just unsafe-formula cells. This is because `ARRAYFORMULA`/`QUERY`/`SORT`/`IMPORTRANGE`-style formulas store their formula text only in the top-left anchor cell — every other cell they visually fill has an empty formula string and no real stored content. The instant the anchor is flattened to a literal, Sheets drops the spill and those cells go blank. Since Apps Script's API can't report a formula's spill boundaries, the only reliable fix is to always re-write every non-blank, formula-less cell from the source's captured value — a real literal gets rewritten with its own unchanged value (harmless no-op), while a spill artifact is correctly preserved. See the block comment above `flattenUnsafeFormulas` in `SpreadsheetDuplicator.js`.
- **Data validation is cleared on every rewritten cell before the value is written.** Sheets enforces "reject invalid input" validation on programmatic `setValues()` calls, not just manual entry. A validation rule whose source list lives on a sheet we just deleted (or that simply doesn't accept the flattened value's type) would otherwise make the write throw. This was found via real testing, not anticipated up front — don't remove it without re-testing against a sheet that has dropdown validation sourced from an excluded sheet.
- **`IMPORTRANGE` cells never depend on the duplicate's own evaluation.** A Drive copy is a new file ID and starts without `IMPORTRANGE` authorization, but since `IMPORTRANGE` is always classified unsafe, its cells are always flattened using the value read from the already-authorized source — the duplicate's own (unauthorized) evaluation of that formula is never read.
- **Only cells holding their own SAFE live formula are left untouched.** Everything else non-blank gets rewritten, even when that means touching more cells than strictly necessary — correctness (no data loss) is prioritized over minimizing write volume or preserving data-validation fidelity on cells incidentally caught by the blanket rewrite.
- **The temp Drive copy's cleanup can't rely solely on `finally`.** If Apps Script hard-kills the execution (the 6-minute timeout, or a manual stop from the Executions dashboard), the process is torn down immediately and `finally` never runs — there's no error to catch and no cleanup code executes at all, so a temp copy is silently orphaned. `deleteFileWithRetry` (retries the trash call with backoff, for transient Drive API failures) only covers the case where `finally` *does* run. The real fix is `cleanUpOrphanedExportTempFiles` in `DriveUtils.js`, called at the start of every export: it self-heals by sweeping the source file's parent folders for leftover `__xlsx_export_tmp__`-prefixed copies older than 15 minutes (comfortably past any real export's runtime, so a concurrently-running export's own temp copy is never touched) and trashes them. Don't remove this sweep in favor of "just fix the finally block" — no code inside the killed execution can run, by definition.
- **`duplicateSpreadsheetFile` passes an explicit destination folder to `makeCopy()`.** Without one, `File.makeCopy(name)` places the copy in the current user's Drive root regardless of where the source lives — a well-known Apps Script gotcha. If this ever regresses back to a bare `makeCopy(name)` call, the temp copy and the orphan sweep above end up looking in different folders and the sweep silently finds nothing to delete, even when orphans exist.
- **There is no public Apps Script API for spreadsheet calculation status.** `CalculationWaiter.js` detects a still-computing cell (a custom function or `IMPORTRANGE` that hasn't resolved yet) only by polling `Range.getValues()` for the literal placeholder string `"Loading..."` that Sheets shows for it — there's nothing else to check. `SpreadsheetApp.flush()` doesn't help here: it only flushes the *calling script's own* pending writes, and the source spreadsheet is never written to. The placeholder text is UI-facing and could in principle vary by locale or Sheets version — verify it empirically (`console.log(JSON.stringify(value))` against a real slow custom function) before trusting the hardcoded `CALCULATION_LOADING_PLACEHOLDER` constant in a non-English spreadsheet.
- **Absence of the "Loading..." placeholder is not proof a cell is done.** A cross-spreadsheet `IMPORTRANGE` read through a script (as opposed to a live browser session that keeps it warm) can briefly report a plausible-but-stale value — e.g. `0` — instead of the placeholder while it's still settling, especially for wide imports or ones wrapped in extra array steps (`LET`/`FILTER`/`CHOOSECOLS`...). This was found via a real export where two of three `IMPORTRANGE` cells on the same row silently got flattened to `0`: the wait loop's first read already showed no `"Loading..."`, and the later, separate read inside `flattenUnsafeFormulas` baked in that same stale value. `waitForCalculationsToFinish` now requires two consecutive polls (`pollIntervalMs` apart) that both show no `"Loading..."` **and** report identical values for every watched cell before it considers the source settled; any change between polls resets the count. Don't revert to a single-read check — it's exactly what let this bug through.
- **The calculation wait watches only the cells `getFlattenColumnIndices` would flatten, not every cell in the included sheets.** A cell holding its own SAFE live formula that's still calculating doesn't matter — it stays a live formula in the export and is never read/frozen, so its transient value is irrelevant. This is why `getFlattenColumnIndices` lives in `FormulaClassifier.js` as a function shared by both `flattenUnsafeFormulas` (which freezes cells) and `buildCalculationWatchLists` (which needs to know, before freezing, exactly which cells to watch) — don't let the two scoping calculations drift apart by reimplementing one inline again.
- **The calculation wait runs before the Drive duplicate and orphan-file cleanup, not after.** If calculation never settles and the wait times out, no Drive copy operation or orphan sweep is wasted on a spreadsheet the export is about to abort on anyway. Known limitation: a formula-less cell where a user manually typed the literal text `"Loading..."` is indistinguishable from a genuinely pending cell — same category of ambiguity as the spill-vs-literal case above. It only affects formula-less cells and surfaces as a named timeout error pointing at the exact sheet/cell, never as silent data loss.

## Testing

No automated test framework exists for Apps Script. `Test.js` has `testEndToEndExport()` — fill in a real scratch spreadsheet ID and Drive folder ID, then run it from the Apps Script editor. See the README's "Testing" section for the recommended scratch-spreadsheet layout that exercises safe formulas, custom functions, `IMPORTRANGE`, excluded-sheet references, and `ARRAYFORMULA` spills.

## Deployment

Script ID is in `.clasp.json`. Push with `clasp push`, then cut a new library deployment (**Deploy > New deployment**, type **Library**) from the Apps Script editor. See the README's "Deploying the library" and "Connecting the library in another project" sections — consuming projects must also declare this library's `oauthScopes` in their own manifest, since Apps Script does not scan a library's code for scope auto-detection.
